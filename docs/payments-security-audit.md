## 1. Findings — High

### H1 · Waitlisted and draft entries are admissible at every gate, including on paid events
- **Evidence:** `src/core/models/payment.ts` `isAdmissiblePayment` returns true for any entry whose `paymentStatus` is absent/`not_required`/`paid` and whose status is not `pending_payment`. A waitlisted entry is never charged and has no `paymentStatus`, so it passes. It also has a ticket: `src/components/student/digital-ticket.tsx` shows the QR for `waitlisted` ("this code activates if a seat opens"). The scanner (`src/lib/offline/scanner.ts` `decideEntry`/`decideMeal`, `src/data/firebase/repositories/attendance-repository.ts` `resolveTicket`), manual entry (`src/app/api/admin/attendance/manual/route.ts`), the wallet route and the rules (`firestore.rules` `admissible()`) all reject only `cancelled` and unpaid. `docs/payment-gateway-evaluation.md` §2.5 item 1 flagged this as an existing gap; the implementation doc's "Admission control built" does not say it is still open.
- **Impact:** a person on the waitlist of a *paid* event can be scanned in and fed without ever paying, and over capacity. For free events it is existing behaviour, so changing it is a product decision.
- **Fix:** make admission an allow-list: admit only `status === "confirmed"` (and decide explicitly for `draft`), plus the payment condition. Put it in one function used by all six places (online `resolveTicket`, offline roster flag, manual route, wallet route, public ticket page, rules `admissible()`), and have the roster flag (`unpaid`) be renamed `notAdmissible`. For free events, either keep today's behaviour behind an explicit decision or apply the same rule — **ask the product owner**; the draft-team text in `src/app/(student)/registered/[registrationId]/page.tsx` already promises "the ticket is not valid at the gate" for drafts.
- **Tests:** unit — `isAdmissiblePayment`/new function for every `status × paymentStatus` pair; scanner unit — waitlisted and draft refused offline and online; rules — attendance/foodCollections create denied for waitlisted and draft; emulator — manual route and wallet route refuse waitlisted on a paid event; component — waitlisted ticket shows no admit-able QR on a paid event.

### H2 · Refunds for a cancelled event are not durable
- **Evidence:** `src/server/payments/lifecycle.ts` `handleEventCancelled` (l.585) runs inside the `PATCH /api/admin/events/[id]` request (`src/app/api/admin/events/[id]/route.ts`, after `ref.update`): it loops every registration, writes a refund record per paid entry, and only *after the loop* calls `executeRefund` for each — all serially, provider calls included. The event is already `cancelled` and the notifications already sent. If the function times out, the process dies, or any `executeRefund` throws (`providerContextFor` throws `ApiError`; see H4), registrations not yet processed have **no refund record**, and nothing re-runs: a second PATCH with `status: "cancelled"` is not a transition, and the cron only retries refunds that already exist (`retryAutoRefunds` queries `openRefunds == true`).
- **Impact:** students paid for an event that was cancelled and are never refunded, silently. The implementation doc states this works "automatically".
- **Fix:** split into two durable steps. (1) In the PATCH, only mark the event cancelled and create refund records in bounded batches (or mark `events/{id}.refundsPending = true`). (2) Have `/api/cron/payments` sweep `events where status == cancelled and refundsPending == true`, create any missing records (idempotent on `reason: "event_cancelled"`), execute them with a per-run budget, and clear the flag when none are open. Return the PATCH even if the provider is down.
- **Tests:** emulator — cancel an event with N paid entries while the provider is down → event cancelled, flag set, no data loss; bring provider up, run the cron → all refunded; kill the sweep midway (throw on the 2nd refund) → next run finishes the rest; running the sweep twice never refunds twice.

### H3 · A fest admin can repoint where money goes; the approval gate is weak
- **Evidence:** `src/app/api/admin/fests/[id]/payments/route.ts`: `PUT` needs only `payment:configure`, which every **admin of the fest** has (`src/core/permissions.ts` `ADMIN`). Approval (`POST`, `payment:approve`, super admin) approves "credentials saved" without checking *whose* merchant account they are: there is no merchant-identity step, no test call to the provider, and no check that the approver is looking at the credentials they think they are. Concretely: (a) an admin saves credentials for their own personal merchant account, and a super admin approves them on the strength of a free-text `merchantRef`; (b) between the approver loading the page and clicking **Approve**, the admin can `PUT` different credentials, and the `POST` transaction approves whatever is stored at that moment (no version/`updatedAt` token); (c) `PATCH /api/admin/fests/[id]` action `transfer` changes the fest owner but leaves the old owner's merchant credentials active (`src/app/api/admin/fests/[id]/route.ts` l.114); (d) `DELETE` of a fest leaves `paymentAccounts`/`paymentSecrets` behind (fest delete is only blocked by events/registrations/certificates).
- **Impact:** an insider can divert student payments to an account the college does not own; the control that is supposed to catch it cannot see what it is approving.
- **Fix:** (1) restrict `payment:configure` to the fest **owner** or a super admin, and notify the fest's other admins and the platform on every change. (2) Add `verifyCredentials(ctx)` to the adapter contract; `PUT` calls it and stores the provider-reported **legal merchant name/id** in `paymentAccounts`; the approval screen shows that name and requires the approver to confirm it matches the institution. (3) Approval takes `{ expectedUpdatedAt }` and fails if the account changed since it was read. (4) `transfer` and fest delete set the account to `suspended` / delete the account and secrets. (5) Log credential changes with actor and provider-reported merchant id (never the credentials).
- **Tests:** emulator — admin who is not the owner gets 403 on `PUT`; approval with a stale token → 409; credentials changed between load and approve → approval refused; ownership transfer suspends the account; fest delete removes secrets; adapter `verifyCredentials` failure blocks the save.

### H4 · Housekeeping is unscheduled, and the retry loop can stall itself
- **Evidence:** `vercel.json` contains only `/api/cron/event-reminders` (daily). `/api/cron/payments` exists but is not scheduled (documented). Consequences with the code as written: lost webhooks are never reconciled (`reconcilePendingPayments`), owed refunds are never retried (`retryAutoRefunds`), and holds on events with unlimited capacity never expire (the on-demand sweep in `src/app/api/registrations/route.ts` only runs when a limited-capacity event looks full, and `limit: 25`). Separately, `retryAutoRefunds` (l.473) is not wrapped in `try/catch`: `executeRefund` → `providerContextFor` throws `ApiError` (provider unavailable, credentials unreadable, test provider disallowed), which aborts the whole run; and it takes the first 50 `openRefunds` documents with no ordering, attempt counter or back-off, so 50 permanently failing refunds starve every later one. `expirePendingHolds` processes up to 500 holds serially with a provider call each.
- **Impact:** stuck money and stuck seats with no signal; one bad fest can block every other fest's refunds.
- **Fix:** schedule the cron (needs an owner decision — it is a deployment setting) at ≤5 minutes; catch per item and continue; record `refundAttempts`/`lastRefundAttemptAt`, order by it, back off exponentially and stop after N attempts by raising a flag for staff; bound each run by time, not just count; add a cheap `GET /api/health` field showing oldest unprocessed hold / open refund age.
- **Tests:** emulator — a refund whose fest has unreadable credentials does not stop other refunds from being retried; 60 failing refunds do not prevent the 61st from being attempted over two runs; a run that exceeds its time budget stops cleanly and the next run continues; hold on an unlimited-capacity event is released by the cron.

### H5 · An amount mismatch can overwrite a payment that was already settled
- **Evidence:** `lifecycle.ts` `applyOrderSnapshot`, l.301–316: the `!amountOk` branch only skips if `pay.status === "needs_review"`. It runs **before** the `settled` check (l.318). So a snapshot with a different amount/currency for any listed order — a stale earlier attempt, or a provider whose order amount changes after a partial refund — flips a `paid`/`refund_pending`/`refunded` payment to `needs_review`, sets the registration's `paymentStatus` to `needs_review` (a confirmed, paid ticket becomes non-admissible), and records `capturedOrderId` of the *other* order. The staff action `resolveReviewWithRefund` would then cancel the registration and refund that other order's amount, leaving the original payment unrefunded.
- **Impact:** a paying student locked out at the gate; refunds applied to the wrong order.
- **Fix:** evaluate `settled` first. For a settled payment, a snapshot for a *different* order with a bad amount is a duplicate-payment case (refund that order, flag it); a snapshot for the *same* order with a changed amount is logged and ignored (or flagged without touching the registration). Only an unsettled payment may enter `needs_review`.
- **Tests:** unit/emulator — paid payment, then a webhook for a second order with a different amount → registration stays `confirmed/paid`, second order refunded; same order re-read with a lower amount (after a partial refund) → no state change; `needs_review` resolution refunds the order that was actually captured.

### H6 · No key rotation, no key versioning, and a single static key
- **Evidence:** `src/server/payments/secrets.ts`: one key from `PAYMENT_SECRET_KEY`; the stored blob has `v: 1` but no key id. `decryptCredentials` fails for any blob not made with the current key. `.env.example` says rotating "needs them re-entered"; there is no re-encrypt tool, no previous-key variable, and no startup check that stored blobs still decrypt. The key sits in the same environment (Vercel project env) as `FIREBASE_SERVICE_ACCOUNT`; anyone who can read both can decrypt every organizer's credentials.
- **Impact:** a key rotation (routine hygiene, or after a suspected leak) takes **every** fest's payments down at once — webhooks return 503 forever (`webhook.ts` → `providerContextFor`), and refunds and checkouts fail — until each organizer re-enters credentials. Losing the key is unrecoverable.
- **Fix:** add `kid` to the blob and accept `PAYMENT_SECRET_KEYS` as an ordered list (`kid:base64,…`), encrypting with the first and decrypting with any; add a super-admin (or script) job `re-encrypt` that rewrites blobs under the newest key and reports counts; add a health check that decrypts one sentinel blob; document backup/escrow of the key. For live, prefer a KMS (envelope encryption) over a raw env key.
- **Tests:** unit — blob made under key A decrypts when A is second in the list and re-encrypts under B; unknown `kid` fails closed with a generic error; emulator — re-encrypt job leaves all accounts working, idempotent; health check goes red when the key is missing.

### H7 · Payment mode/provider is not bound at the points where money is touched
- **Evidence:** `payments/{id}` records `provider` and `mode` at hold time (`writeHold`), but `executeRefund` (l.448), `verifyWithProvider` (l.546), `ensureCheckout` and `processWebhook` use whatever `paymentAccounts/{festId}` says *now*. An admin can `PUT` different credentials/mode at any time (it resets status to `pending_review` but webhooks, refunds and reconciliation keep working with the new credentials).
- **Impact:** after a sandbox→live switch (or any credential change), a hold created under the old credentials is verified with the new ones: `fetchOrder` returns "unknown → failed", the registration is marked `failed`, and a customer who really paid is shown a failure; refunds for an old payment are attempted against the wrong merchant account (fail, or refund a different transaction). The reverse can mark a sandbox test payment as real.
- **Fix:** store the account's `credentialsVersion` on each payment; if it differs from the account's current version, do not call the provider with the new credentials — put the payment in `needs_review` and surface it. Refuse a mode change while the fest has non-terminal payments or open refunds. In `executeRefund`, require `pay.provider === account.provider && pay.mode === account.mode`.
- **Tests:** emulator — change credentials while a hold is pending → webhook/recon do not mark it failed, it goes to review; mode change blocked with open payments; refund after a credential change is held, not sent.

## 2. Findings — Medium

**M1 · Refund execution has no claim/lease and relies on the provider for idempotency.** `executeRefund` reads the record outside a transaction and calls the provider; the webhook, `approveRefunds`, `retryAutoRefunds` and `handleEventCancelled` can all run it concurrently. The fake provider is idempotent per refund id; real gateways commonly answer a repeated refund id with an *error* ("already exists"), which `recordRefundOutcome` records as `failed` — and a `pending → failed` regression is allowed (only `success` is protected), after which retries repeat forever. Fix: claim with a transaction (`refundLockedUntil`), make the adapter contract state "on duplicate id, return the existing refund's status", never move `pending` back to `failed` without a provider read. Tests: concurrent `approveRefunds` ×2 + cron → provider sees one call per refund id; duplicate-id error maps to the existing status.

**M2 · Refund webhooks are trusted at face value.** `webhook.ts` applies `event.status` from the signed body to `recordRefundOutcome`; unlike payments it does not re-read the refund from the provider, and `amountPaise` in the event is never compared with the record. Signed, so not forgeable by outsiders, but a replayed old `success` for a refund id that later failed, or a provider quirk, changes money state unverified. Fix: add `fetchRefund` to the adapter and use the webhook only as a hint; compare amounts. Tests: webhook says success while provider says failed → stays failed; amount mismatch → flagged.

**M3 · Work done before the signature is checked.** `processWebhook` parses the body, reads `payments/{id}`, `paymentAccounts`, `paymentSecrets`, and decrypts credentials before `verifyWebhook`. An unauthenticated caller costs three reads and an AES decrypt per request (rate limit is per IP, 300/min, `public.webhook`), and the response distinguishes "order exists" (401) from "unknown order" (200 `ignored`) — an existence oracle on 20-character Firestore ids (low value, but unnecessary). Fix: for providers that put a merchant identifier in the header/path, resolve the account from that; otherwise cache decrypted contexts briefly and answer identically for unknown and bad-signature cases (always 401, or always 200 with no body difference). Tests: timing/shape of the two responses is identical; rate limit applied (needs a test with the limiter on).

**M4 · Secret scrubbing in logs/telemetry is by convention only.** Verified clean today: no code path logs credentials, the PUT response and audit entries contain field names only, `paymentSecrets` is denied to every client, and error messages from `secrets.ts` are generic. Not guaranteed going forward: `src/server/errors.ts` `logError`/`describeError` log message and cause chains, and `captureException` sends them to Sentry; `sentry.server.config.ts` `beforeSend` scrubs headers but not `event.request.data`; a real adapter's HTTP-client error will often include the request URL/body. I could not confirm whether `@sentry/nextjs` attaches the request body for App Router route handlers in this version. Fix: scrub `request.data` and any `extra` for `/api/admin/fests/*/payments` and `/api/payments/*`, redact values of keys named like the adapter's `credentialFields` in `describeError`, and give adapters a `safeError()` wrapper. Tests: unit — throw an error whose message contains a credential value inside an adapter call → logged line and Sentry event contain `[redacted]`.

**M5 · Seat-hold squatting.** One account can hold one seat per event, but can re-register as soon as the hold expires and hold seats on many events at once (20 registrations/min per account). With a handful of verified accounts someone can keep a capped paid event "full" for the hold period repeatedly. Fix: cap concurrent unpaid holds per account (e.g. 3), add a cool-down after N expired holds on the same event, and consider shortening holds when an event is nearly full. Tests: 4th concurrent hold refused; third expiry on one event triggers a cool-down message.

**M6 · No operational visibility for money events.** Staff actions are audited; the *automatic* ones are not: payment confirmed, duplicate payment refunded, late payment refunded, `needs_review`, refund failed, event-cancel refunds. No notification reaches staff for `needs_review`, `refund_pending` or a refund that keeps failing, and the admin UI has no payments list or reconciliation view. A stuck `needs_review` also keeps its seat held indefinitely. Fix: audit-log every state change that moves money, notify fest admins on `needs_review`/failed-refund, add a payments tab (status counts, oldest open item, export for reconciliation against the provider's settlement report). Tests: each automatic transition writes one audit entry; `needs_review` creates an admin notification.

**M7 · Offline/stale scanner roster after a refund (the reported issue — assessed).** Confirmed and slightly wider than reported: `decideEntry`/`decideMeal` decide **locally from the cached roster even when online**; the server only sees the scan later in `syncQueue`, where a refused scan is simply dropped (`scanner.ts` l.522–526) while the person has already been admitted and the local record says "checked in". The roster refreshes every 120 s when online (`useScannerSync`) and never when offline. So a refunded or event-cancelled ticket is admissible for ≤2 minutes online and for the whole offline period; a refund approved just before the gate can be defeated by a pre-loaded phone. Also the reverse: a payer confirmed after the roster was cached is turned away until the next refresh (safe direction, but an availability complaint). Mitigations, cheapest first: (1) when online, make the scan check the single registration with the server (`getByTicketCode`) before showing "ok", falling back to the roster only when offline; (2) show the roster's age on every result and block entry for rosters older than a configurable maximum (e.g. 15 min) unless the volunteer overrides with a reason; (3) include a small signed **revocation list** (ticket codes refunded/cancelled since T) in the roster refresh and apply it on every scan, refreshed on each sync; (4) when a queued scan is later refused for payment/cancellation, flag it prominently in the admin attendance view and the scanner history ("admitted but not valid") instead of silently dropping it; (5) for refunds approved on event day, make "approve refund" show the number of devices/scanner sessions that have a roster older than the approval. Do (1) and (4) before live; (3) if offline gates are a requirement. Tests: scanner unit — online scan of a ticket refunded after the roster was cached is refused; offline scan with a roster older than the limit is blocked/overridden with a logged reason; sync of a refused queued scan marks it "admitted — invalid" and appears in attendance reconciliation.

**M8 · Redirect target not validated.** `src/components/student/payment-panel.tsx` calls `window.location.assign(result.redirectUrl)` with whatever `ensureCheckout` returns from the adapter. An adapter bug or compromised provider response could send users to an arbitrary URL (`javascript:` URLs also execute via `assign`). Fix: validate on the server in `ensureCheckout` (https only, host allow-list per adapter) and again on the client. Tests: adapter returns `javascript:`/`http:`/foreign host → 502, nothing returned.

**M9 · Events can leave a paid state without a refund path.** `PATCH /api/admin/events/[id]` only handles `cancelled`; setting a paid event to `draft`, `archived` or `completed` while it has paid entries leaves them paid with no refund and, for unpublished events, stranded holds. Fix: refuse those transitions while paid entries exist (offer "cancel and refund") or handle them like cancel.

**M10 · Rate limits and App Check are untested for the new routes.** The emulator project sets `RATE_LIMIT_DISABLED=1` (`tests/setup/emulator.ts`), so `authenticated.checkout` and `public.webhook` are never exercised, and no test sends the payment routes through App Check enforcement.

## 4. Verified as sound (what I checked and found correct)

1. **Credential storage:** AES-256-GCM, random 96-bit IV per encryption, auth tag verified, fest id bound as AAD (a blob copied to another fest fails to decrypt) — `secrets.ts`. Verified by `tests/unit/payments.test.ts` and `tests/emulator/payments.test.ts` ("stores credentials encrypted").
2. **Credential exposure:** `paymentSecrets` and `paymentAccounts`, `payments`, `paymentEvents` are explicit `allow read, write: if false` in `firestore.rules` and tested for anonymous, student, volunteer, own-fest admin and other-fest admin. The settings API returns only `credentialsSaved`; tests assert the secret string is absent from the response, Firestore document, audit log and account document.
3. **Webhook signature over the raw body:** the route reads `request.text()` once and passes the same string to `peekWebhook`/`verifyWebhook`; the test provider uses HMAC-SHA256 with `timingSafeEqual` and rejects missing/wrong/altered signatures. Signature secret is **per fest**, so a valid signature for fest A cannot confirm fest B's order (the order's own fest decides which secret is used).
4. **Never trust the body:** payment webhooks only trigger `fetchOrder`; `applyOrderSnapshot` re-checks order↔registration membership (`orderIds`), amount (`amountPaise`), currency (`INR`) inside a transaction. A forged "paid" body for an unpaid order is tested and confirms nothing.
5. **Idempotency/ordering:** duplicate deliveries (same event id → ledger; different event id → `samePayment` no-op), failed-then-retry on a new order id, second paid order refunded without touching the registration, late payment reinstated or refunded, payment after cancel refunded — all tested. Transitions run in Firestore transactions that read the registration, payment and event; concurrent expiry vs confirmation vs cancellation serialize and converge (I walked each pair: expire/confirm, cancel/confirm, reinstate/register, promote/cancel; none can yield a paid registration without a counted seat or two tickets — there is one `ticketCode` per registration, created before payment and unusable until admissible).
6. **Capacity:** unpaid holds count via `occupiesSeat` but not `holdsSeat`; counters move with the same increments in create, cancel, expire, promote and reinstate; the registration transaction re-reads the event. Concurrency is tested (`never exceeds capacity under simultaneous requests`) with the usual emulator caveat that losers may see 503.
7. **Authorization:** students cannot write any payment field (`firestore.rules` owner update allows only `status`/`cancelledAt`/`updatedAt` from `confirmed` with `paymentStatus` absent or `not_required`; tested for hold, paid and unpaid entries). `payment:approve` is super-admin only; an admin approving their own account gets 403 (tested). Every new admin route calls `requirePermission` and `requireFestAccess` with the registration's/fest's `festId`; other-fest admins get 403 (tested for configure, review, refund). Checkout is owner-only and answers 404 for others.
8. **Flags:** with nothing set, `paymentsEnabled()`, `livePaymentsEnabled()` and `testProviderAllowed()` are false; `getAdapter` returns no provider in production; paid registration is refused rather than silently made free; `PUT` of the `test` provider is refused when not allowed. All covered in `tests/unit/payments.test.ts` and the emulator suite, and `validateEnv` reports half-configured setups (`tests/unit/env.test.ts`).
9. **Cron authentication:** `/api/cron/payments` returns 401 without `Authorization: Bearer $CRON_SECRET` and when `CRON_SECRET` is unset (tested). It is not in `vercel.json`, so it cannot run in production today.
10. **Expiry behaviour:** a lapsed hold is only released after the provider is asked; provider-down keeps the hold for up to 1 h (`PROVIDER_UNREACHABLE_GRACE_MS`) then releases, and a late payment is reconciled (tested). Holds with money attached (`paid`, `needs_review`) are never discarded by the sweep.

## 5. Payment state machine — transition review

States (payment doc): `created → pending → paid | failed | needs_review`; `failed → created` (new attempt); `paid → refund_pending → partially_refunded | refunded`; `pending/failed → expired | cancelled`. Registration `paymentStatus` mirrors this.

| Transition | Where | Verdict |
|---|---|---|
| created→pending | `ensureCheckout`, `applyOrderSnapshot` (pending) | OK; update is conditional on `created` (cannot overwrite `paid`). |
| pending→paid (confirm) | `applyOrderSnapshot` | OK; amount/currency/order verified; **but see H5 ordering**. |
| any→needs_review | `applyOrderSnapshot` | **Defect H5** for settled payments; OK for unsettled. |
| pending→failed | `applyOrderSnapshot` | OK; guarded against settled/needs_review. A registration whose `paymentStatus` is `failed` still holds its seat until expiry (intended). |
| failed→created (retry) | `ensureCheckout.startNewAttempt` | OK; compare-and-set on `attempt`. Two simultaneous retries create one attempt. Old attempts stay in `orderIds` and are still honoured (duplicate → refund). |
| pending→expired | `expireOne` | OK; transaction re-checks status, hold time and payment status; provider consulted first. |
| expired + late paid → reinstated/refunded | `applyOrderSnapshot` | OK; requires `reg.paymentStatus === "expired"`, published event, free seat, no other active entry. Does **not** check fest `registrationState` or registration deadline (reinstating into a closed fest is arguably right — seat was paid for — but should be a conscious decision). |
| paid→refund_pending | `writeCancellation`, `handleEventCancelled`, late/dup paths | OK per-path; **H2** durability; amount excludes only successful refunds of the primary order (a second concurrent path could double-request, but the paths are state-exclusive: each requires `paymentStatus` to be a specific value inside the same transaction). |
| refund_pending→refunded | `recordRefundOutcome` | OK; duplicate-order refunds never change the registration's payment status. **M1** pending→failed regression. |
| needs_review→refund_pending | `resolveReviewWithRefund` | OK for the captured order; no path to accept a mismatched payment (intentional). |

**Races examined and found safe:** double webhook ×2 (both reach the same transaction; second sees `paid`); webhook vs cron reconcile; student cancel vs webhook (cancel reads `pending`→ cancels, payment then auto-refunded; or reads `paid` → queues refund); event cancel vs webhook; staff promote vs student cancel (both read the registration in-transaction). **Races I could not close by reading:** two simultaneous `executeRefund` calls (depends on provider idempotency, M1); two simultaneous `PUT`s of credentials (last write wins, acceptable).

## 6. Capacity, waitlist, teams, cancellation

- **Holds / expiry:** per-registration `holdExpiresAt`; on-demand release when a limited-capacity event looks full (`registrations/route.ts`), cron otherwise (unscheduled — **H4**).
- **Waitlist promotion:** all three promotion paths (student cancel, expiry, staff) create a payment hold on a paid event, never a ticket; if the fest can no longer take payment the entry stays waitlisted. Verified by tests. The promoted person's clock starts at promotion, so a waitlisted student can be promoted at night and lose the seat before reading the email (consider a longer promotion hold; product decision).
- **Teams:** one charge per registration; roster mutations (join code, invite, remove, accept, decline) are refused while `pending_payment`; invitations/emails are sent after payment. A paid team below its minimum becomes a paid `draft` with no deadline-refund (documented). Draft teams are admissible at the gate (**H1**).
- **Cancellation / event cancellation:** unpaid holds release without charge; paid cancellations queue refunds for staff (no student self-service refund — business decision); event cancellation **H2**.
- **Concurrent registration:** tested; see §4.6.
